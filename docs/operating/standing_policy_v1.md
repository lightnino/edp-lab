# Standing 0A infrastructure policy and P5 broker

At 0A, the owner installs one signed `EDP_STANDING_POLICY_V1` document outside the Agent worktree. Its signed `document` contains `policy_id`, `issued_at`, `expires_at`, `universe_path`, `universe_sha256`, `cohort_pattern`, `routes`, `max_increment`, `output_prefix`, `contracts` (name → exact `version` and `sha256`), `operations`, `databricks_path_prefixes`, `databricks_table_prefixes`, `git_operations`, `protected_branches`, `limits` (runtime seconds, compute units, token count, retries, operations), and `grant_hours`. The policy is reviewed once for its bounds, not per selected cohort. A changed parser/model/rule or new economic rule requires a policy amendment after semantic approval.

The P1/P2 roster and checkpoint are inputs to the later queue; selection is never repeated just to issue authority. The queue supplies `sources` as exact identity/path/SHA triples, `previous_cohort`, and `prior_receipt`. The prior receipt is independently signed `EDP_PRIOR_COHORT_RECEIPT_V1` with `authority: protected-verifier-v1`, `cohort`, exact `identities`, their canonical `roster_sha256`, the accepted `result_freeze_sha256`, `status: VERIFIED` and `live_readback: true`. The verifier must derive this receipt from the accepted version-pinned prior result and frozen cohort, not the Agent's assertion. P5 checks prior membership, incremental disjointness, cohort size, Universe SHA, holdouts, every selected RAW hash, contract pins, route, operations, destinations and limits. Unknown or exhausted scope is denied. The source-preserving `CORPUS_ONLY` route may be allowed under a standing policy; new semantic routes require an approved pinned contract and explicit policy scope.

The protected broker issues a short-lived exact `EDP_SIGNED_GRANT_V1` using its own Ed25519 key. The Agent can request and read the grant, but cannot edit the policy, broker key, revocation list, service deployment, protected ledger or Databricks/Git credentials. The Runner uses `auto` as its grant argument and verifies the broker signature with `broker_ed25519_public.pem` in `EDP_OWNER_TRUST_DIR`. Exact operation boundaries reload it before each external write. Independent signed stage, operation, timing and final live freeze receipts are still required; a grant is never a result receipt. Revocation or expiry fails closed. The owner-signed legacy grant format remains only for historical reproduction.

## One-time protected deployment

An infrastructure owner must provision independent broker and verifier identities, a protected trust directory and Unix socket, pin the reviewed service code, install the owner-signed policy and independently verified C1500 prior-cohort receipt, create broker/verifier signing keys and public keys plus the owner public key, initialize `revoked_grants.json`, and protect the grant store and operation ledger. The private keys and credentials must never be exposed to Codex or an agent-writable worktree. Run `python -m edp_lab.operating.policy_broker SOCKET ROOT POLICY TRUST BROKER_KEY GRANT_STORE` as the broker identity and set `EDP_POLICY_BROKER_SOCKET` and `EDP_OWNER_TRUST_DIR` for the Runner. The verifier service must derive and sign run-specific live receipts from Databricks and Git readback, without per-run owner signing. A protected supervisor must resume `VALIDATING` checkpoints when those receipts arrive. The write adapters and credential holder must also execute in the protected runtime. Verify socket permissions, service code pin, revocation, append-only ledger retention and a negative unauthorized-write test before live use.

This repository implements and tests the evaluation, grant issuance and Runner request path. It does not install the protected service, attest C1500 membership, move credentials, or claim a live C2000 run. Those operations require owner-controlled infrastructure outside this writable workspace.
