## Authority and source boundary

The initial source is the SEC Financial Statement Data Sets (FSDS) `num.txt` member. `SEC_FSDS` means this specific publisher/dataset/record family, not all SEC filings or all XBRL datasets. Preserve every source delivery under its admitted `source_instance_id`, immutable RAW path and SHA-256, exact `num.txt` member SHA-256, approved binding, pinned M1/M2 Delta version, source field ordinal/name and lexical text. [Source Identity](source_instance_identity.md), [M1](day2_c300_m1_readiness_v1.md), [M2](m2_additive_typed_numeric_v1.md), [historical M2](historical_c750_m2.md), and the [C1500 result freeze](../metadata/freezes/O_C1500_M2_v1/databricks_result_freeze_v2.json) are inherited; this proposal grants no new parser, numeric, semantic or economic rule. `metadata/sttm.csv`, `metadata/entity_crosswalk.csv`, and [Agent V2's ERD](agent_v2_candidate_erd.md) remain candidate observations, not Business Key authority.

The SEC's [current FSDS documentation](https://www.sec.gov/files/financial-statement-data-sets.pdf) calls `adsh` the accession number of an EDGAR submission; it identifies SUB rows and references them from NUM. It defines `tag` with `version` as the taxonomy-scoped tag identifier, with custom tags using the defining accession as version. It identifies the source NUM row key as `adsh, tag, version, ddate, qtrs, uom, segments, coreg`. This is a publisher claim about its row layout, not proof that the retained snapshot is collision-free. The [SEC dataset page](https://www.sec.gov/dera/data/financial-statement-data-sets.html) describes the December 2024 reprocessing and added `segments` field. No later or alternate delivery is silently substituted for a frozen one.

## D1 Filing candidate

**Rule for review:** admit exact nonblank `adsh` under `SEC_FSDS` as a source-native submission reference. A repeated value in NUM associates multiple amount observations with the same filing reference. A repeated value in a later physical delivery would associate to the same native reference only after checking the publisher namespace, as-filed accession text and source provenance; each delivery/record remains independently retained. Do not equate a filing with an issuer or registrant, and do not choose an original/amendment or latest submission. `SUB.form` ending `/A` is an amendment marker observation, not authority or a historical alignment rule. Any collision of one `adsh` with conflicting SUB identity attributes is an explicit `UNRESOLVED` exception before Hub promotion.

## D2 Concept candidate

**Rule for review:** exact `(SEC_FSDS, tag, version)` can name a source-native tag definition reference. Standard taxonomy version and custom-defining accession are distinct forms of `version`; both remain opaque strings. `tag` alone is `REJECTED` because multiple observed versions share text. Equal `tag` text across releases or custom submissions does not establish equivalent accounting meaning. Variant spellings remain distinct tokens. If the version is absent, retain the occurrence without creating a Concept Hub reference; never fill it from another delivery or the current taxonomy. Revisit semantic equivalence only with reviewed taxonomy definitions and temporal scope.

## D3 Reported observation and context

Preserve the original context tuple in field order: `adsh, tag, version, ddate, qtrs, uom, segments, coreg`, followed by `value` and `footnote`. The first eight fields are the SEC-published NUM row-key claim; the retained three-member check disproves uniqueness in this scope. `value` and `footnote` distinguish some observations but do not constitute a proven Business Key, and one exact-equal pair remains distinct. `segments` is essential: omitting it creates 837,990 groups with multiple segment variants in the inspected scope. Empty `segments`, `coreg`, `value` and `footnote` are preserved as present empty text, not coerced to SQL NULL or a business missing value.

A **Business Fact** would require a reviewed meaning, identity and correction policy; none is established. A **reported Fact Observation** is a row of the retained NUM member with its exact context and payload. A **Record Occurrence** is the physical source interval for that row (or a header/framing row). The observation is anchored to the physical occurrence for V1. Repeated observations across deliveries and amendments stay separate. A future relationship grain could add a publisher-provided fact ordinal/identifier if one is evidenced, or use a reviewed dependent-child key with a source-stable qualifier. The current FSDS NUM data and approved parser provide no such universal semantic qualifier. The physical locator may distinguish observations technically but must not be relabeled a Business Key.

## D4 Satellites, hashdiff and history

`S_NUM_LEXICAL` stores all ten NUM fields as an ordered array of `(field_ordinal, original_name, lexical_value, presence_state)` and the exact approved parser/model/rule versions. In accepted M1 DATA rows every field position is physically present; `PRESENT_EMPTY` and `PRESENT_TEXT` distinguish empty and nonempty strings, including whitespace-only strings. `ABSENT` is reserved for a structurally absent source field in a separately recorded failure/exception; no invented NUM value or source NULL token. The immutable RAW byte interval and member SHA allow byte-level reconstruction, including quoted text and embedded TAB. The approved scoped parser determines the ten field values; a naive TAB split is not authoritative for the `SRC000054` witness.

`S_NUM_M2_VALUE` is an additive projection keyed by the same technical occurrence plus ordinal 9, with exact lexical reference, `value_decimal`, conversion outcome/reason and `M2_ADDITIVE_TYPED_NUMERIC_V1`, `EXACT_DECIMAL_38_4_V1`, `FSDS_NUM_VALUE_SCOPE_V1`. Its SQL NULL means no typed value, not source business NULL. The historical frozen M2 output covers exactly 60 FSDS `num.txt` bindings; N450 and new N750 sources are not implicitly eligible. Later rules must be versioned and separately approved.

**Proposed hash specification:** `SHA-256` over bytes `EDP_VAULT_PROPOSAL_V1` plus a zero byte, then a sequence of UTF-8 fields. Each present field has an unsigned four-byte big-endian length followed by its exact bytes; an absent field uses `0xffffffff` length with no payload. The first field is a domain string, such as `H_FILING`, `H_CONCEPT`, `SOURCE_OCCURRENCE`, or `FSDS_NUM_LEXICAL_PAYLOAD`. Hub hashes serialize exact namespace and Business Key components in named order; the occurrence hash serializes exact `source_instance_id, archive_member, decimal byte_offset, decimal byte_length`. The lexical hashdiff serializes field count, then each ordinal, original name, presence state and exact lexical value in ordinal order. No trimming, case-folding, numeric normalization, date parsing, delimiter joining or SQL NULL/empty conflation. A hash collision must be checked against the stored components and fail closed. `run_id`, load timestamp and source time are excluded from Hub and occurrence hashes. The example implementation in `scripts/day6_vault_occurrence_probe.py` is a probe, not a production key library.

Equal lexical payloads can share a hashdiff while having distinct occurrence keys. A changed value or footnote changes the hashdiff; a repeated delivery keeps its distinct Source ID and occurrence key even if text is equal. Replay of the *same* pinned RAW interval yields the same occurrence key and payload hashdiff while producing a separate load event. Append-only history retains all physical occurrences, their payload versions, parser-rule versions and audit events. If a newly approved parser produces different lexical fields from the same physical interval, retain both versioned derivations and raise a conflict for review; never rewrite the earlier one. Corrections in a new filing/delivery are additional observations, with no inferred supersession.

`load_timestamp_utc` is the actual warehouse ingestion time. `ddate` is the SEC-defined period end date rounded to month end, `qtrs` is reported quarter count, and `SUB.filed`/`accepted` are source filing time fields when separately joined under an approved relationship. None is a load time or a proven business-effective `valid_from`/`valid_to`. Late-arriving deliveries append; source ordering, amendment status and source business time remain attributes rather than ordering authority.

## D5 Technical occurrence and lineage

The proposed stable locator is `(source_instance_id, archive_member, byte_offset, byte_length)` for the immutable, SHA-verified member. Store and verify `source_line`, `binding_sha256`, member SHA, RAW SHA, RAW path, parser profile/version, M1 rule/model, record kind, and the member's expected ordered header. `source_line` and interval must agree with the approved parser's one-physical-line contract; byte intervals must cover the member without gaps or overlaps when a full binding is validated. The field locator is `(technical occurrence key, field_ordinal)` with the original name. `run_id` is an execution reference, not part of physical identity. `binding_sha256` is a versioned interpretation reference and integrity check, not a substitute for the physical Source ID/member/interval. Identical row bytes at two offsets have different technical keys. A changed RAW SHA under the same Source ID or a changed interval for the same key is an integrity failure, not a new history version.

For full binding execution, assert one parent binding per record, unique physical intervals, exact total/member SHA, correct header/framing counts, `DATA × bound field width` field occurrences, original lexical multiset and duplicate multiplicities. For replay, compare occurrence keys and payloads excluding run ID and load timestamp, then record the new execution event. The bounded Day 6 probe only re-read five selected lines twice; frozen M1 validation supplies the larger existing integrity evidence. No Day 6 Vault rows were created.

## Explicit exclusions and consolidated owner review

No enterprise issuer/security/listing/manager integration, cross-source accession equivalence, taxonomy-concept merger, economic fact identity, amendment precedence, correction winner, financial unit conversion, source-NULL semantics, reporting-period equivalence or effective-validity interval is approved. `ddate`, `qtrs`, `uom`, `segments` and `coreg` are source context, not a canonical reporting period or entity relationship. The older Agent V2 candidate ERD remains a separate bounded candidate exercise; this proposal does not promote its crosswalks or STTM mappings.

The owner review should decide **together**: (1) whether the two exact source-native Hub Business Keys are acceptable and at what FSDS snapshot/namespace scope; (2) whether to approve only the filing–concept reference Link while leaving Business Fact identity unresolved; (3) whether the occurrence-anchored Satellites and hash serialization are acceptable as a source-scoped V1 prototype; and (4) what additional source evidence, if any, would justify a fact dependent-child identifier or a cross-delivery equivalence rule. Approving D4/D5 mechanically does not approve D1–D3 semantically. A different choice can retain the lossless occurrence prototype; a premature context Link would merge the 51 observed collision groups.
