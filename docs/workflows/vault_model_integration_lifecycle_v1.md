# Vault Model & Integration Lifecycle V1

**Status: OWNER-APPROVED WORKFLOW SPECIFICATION — not a deployed agent, execution grant, or completed full-corpus Vault integration.**

**Purpose:** Given a frozen, authorized source population and an accepted source-preserving representation, identify applicable source-native business identities and relationships, reuse or propose versioned Data Vault contracts, load the approved population into Delta Vault, prove source fidelity and relationship integrity, and freeze actual platform results.

**Operating principle:** One-time bounded infrastructure setup with independently demonstrated end-to-end operational readiness, evidence-led model reuse, conditional prototype, autonomous diagnosis and checkpoint-safe execution, and selective human decisions only for new business meaning, authority or integrity exceptions. Routine preflight, technical repair, tests, readback and already-authorized execution are agent responsibilities, not recurring manual approval stages.

## Position in the architecture

- **Universe Lifecycle** owns acquisition, retained RAW candidates, membership, holdouts and provenance approval. Vault never expands Universe membership or stages/mutates RAW.
- **Cohort + Model Lifecycle** owns admitted source-preserving RAW → CLEAN → QUERYABLE processing and its own model/stability outcomes. Vault may consume its *actual immutable, version-pinned outputs*; it does not repeat admission or RAW→CLEAN. The two are **separate lifecycle orchestrators with a data dependency**, not competing versions of P0–P14.
- **This Vault Lifecycle** owns source-family Model Fit, source-native Hub/Link/Satellite modeling, versioned Vault Mapping Contracts, Vault Delta loading, relationship integrity, Vault regression and Vault result freeze.
- **Validation, Stability, Live Freeze + Git Exit V1** and **evaluation_contract.md** supply reusable Lossless 1–6, economic applicability, negative-oracle, performance-evidence and acceptance principles; Vault invokes the applicable assertions **against Vault outputs**, adding Vault-specific keys/links/history tests. Do not copy the Cohort DAG, redefine conflicting oracles or reprocess upstream data.
- **Agent Operating Contract V1** governs trusted authority, independent observation, decision escalation, liveness, and recovery classification. **Agent Operating Guide V1** provides generic procedures. Reuse utilities only when interfaces/authority fit; no forced shared lifecycle engine.
- **Source-family Vault Contracts** own approved business identities, grains, relationships, mapping rules and semantics. This workflow is source/cohort-neutral. For example, docs/vault_load_contract_v1.md applies only to its explicitly approved SEC FSDS num.txt scope, not to every source.

**Inputs:** Frozen source roster and source/RAW identities; applicable Universe membership authority; pinned M1/M2/other source-preserving representations and model/parser/version hashes; prior accepted Vault outputs if any; installed execution permissions/policy; approved source-family Vault contracts; validation registry; actual compute/resource boundaries.

**Output:** Versioned model/contract decisions, exact per-source disposition and coverage, real Delta Hub/Link/Satellite/occurrence/history results, applicable Lossless + negative + regression evidence, operating metrics, actual Vault freeze and Git exit. Never equate “roster registered,” “technical occurrences retained,” or “prototype passed” with full semantic Vault integration.

## Authority, reusable model and acceptance rules

1. **Approval granularity:** One-time infrastructure authorization applies only to its installed scope. Source-family business identity, Link relationships, grains, amendment precedence, economic semantics and consequential corrections require explicit owner approval when new/changed. Authorized repeat loads/validation do not require another owner signature. Expanded write populations, tables or resource limits beyond the actual grant require scope authorization; a bounded prototype's approval cannot silently authorize a full corpus.
2. **Technical vs semantic coverage:** Every selected physical source receives a terminal disposition. “Technical occurrence retained” alone is NOT “business Vault integrated.” Report fully modeled/loaded, technically preserved-only, unsupported, blocked and failed separately, with counts adding to the frozen source roster and accountable record totals.
3. **Branching and integrity:** V3 requires a material trigger and a matching signed E2E readiness/admission check before external writes; do not skip V5 after a new load. Conditional V6 depends on an actual prior Vault baseline or compatibility change. Initial full-population loading does not erase or overwrite an existing bounded prototype. Hard conflicts, stale readiness and unresolved external effects are blocked, not reinterpreted or replayed automatically.
4. **Agent autonomy:** Agent plans and drives stage selection, E2E preflight and reusable readiness evidence, applicable tests, read-only investigation, bounded technical repair, checkpoints and independent acceptance. One consolidated Owner decision is required only when installed authority cannot safely proceed. **No universal Agent V4 evaluation stage:** a Day-specific pilot may score diagnostic quality, autonomous completion and human minutes from V7/V8 evidence without making that mandatory for all Vault runs.
5. **Cross-lifecycle interface:** Vault consumes independently accepted upstream sources/results as inputs. The shared Validation specification is a callable acceptance rulebook, not a third data-processing engine. The Operating Contract and Guide are cross-cutting controls, not a reason to merge Vault and Cohort orchestration.
6. **Truthful completion:** A document, local unit test, frozen manifest or successful small prototype is not evidence that a larger Delta Vault load occurred. Stage PASS requires actual appropriate live evidence. Publishing this specification does not itself install privileges or authorize a full-corpus integration.

## Run-specific configuration

Bind each real execution to a separate approved source roster/freeze, approved contract versions, historical results, actual authorized output scope and budget, and an accepted prototype reference if applicable. These are **run inputs/evidence, never hard-coded workflow rules**. A saved Pilot Evaluation is not a blanket authorization for a later larger workload.
