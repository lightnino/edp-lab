## Proposed protected V4 execution solution, not an installed permission

The installed signed Vault V2 policy has `c2000_full_integration_allowed=false`, an exact eight-table prototype allowlist and a 1,000-DATA-occurrence run cap. At 321,150,341 rows, its 1,000-row cap implies at least 321,151 runs, before any additional member/table work, beyond the installed grant and statement budgets. The existing inline Warehouse SQL loader is therefore not a full-source solution. The existing shared Warehouse `589e80595c7c8cb8` remains for bounded metadata/readback; **no new Warehouse is proposed**.

Engineering candidate: fixed, hash-pinned Databricks Spark Jobs runtime consuming the frozen source manifest and approved family contracts, with source/member partitions, immutable occurrence anchoring, insert-only/idempotent Delta merge, and persisted per-source/member input/output/failure ledger. A protected service checks an Owner-signed scope, exact runtime/deployment SHA, roster/manifest SHA, family-contract hashes, namespace and table allowlist, job compute configuration, per-batch row/time limits and zero retry. It reserves a batch outside the worktree **before** Jobs submit; a timeout or missing run ID becomes `UNCERTAIN_REQUIRES_READBACK`, never a replay. Jobs success is followed by independent persisted Delta counts, lineage, key/cardinality and quarantine checks before V4 PASS. `src/edp_lab/vault/full_scale_boundary.py` and `full_scale_job.py` implement candidate request/freeze shape, one-shot reservation/submission and unsigned Jobs readback; tests use fake transport. No protected service was installed, no runtime deployed, and no write attempted. Business mapping code for the four candidate contracts must follow Owner semantics and bounded V3 tests.

**Resource evidence:** retained RAW files are about 8.25 GB compressed/on disk across the four families (FSDS 5,453,244,668; 13F 2,095,301,115; EDGAR 697,095,801; Treasury 2,299,582 bytes). FSDS uncompressed NUM is 23,121,177,430 bytes; other three members total 6,455,318,372 bytes. The 13F largest member is 87,012,867 INFOTABLE rows. An initial **candidate** cap of 2,000,000 DATA rows/batch requires at least 161 batches by arithmetic; a 240-batch, 3,600-second/batch ceiling would allow up to 240 compute hours, with zero automatic retries. This is a conservative authorization *ceiling for discussion*, not a throughput prediction, DBU/$ estimate, or guarantee that 240 partitions suffice. Before full release, run approved bounded family benchmarks, measure rows/sec, peak compute, shuffle, Delta merge duration and DBU/$, and stop if projected completion exceeds the Owner's approved budget. No comparable full-source Spark benchmark exists yet, so the Owner must set an explicit DBU/$ ceiling or approve a measured conditional envelope; unmeasured cost cannot be reported as zero.

The eight existing prototype Delta tables represent FSDS NUM only. The four proposed contracts require **new** named Hub/Link/Satellite or assertion structures, a versioned schema migration and an exact allowlist after semantic approval.
